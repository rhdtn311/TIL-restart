# 학습 계획: [JVM] Heap 메모리 구조와 GC

## 실무 맥락

2026-04-06, 데이터 마이그레이션 자동화 서비스에서 110MB xlsx 파일(2200열 × 17000행) 검증 중
OOM이 발생했다. `jstat -gc`로 상태를 찍었는데 `OU`, `EU`, `YGC`, `FGC` 같은 컬럼이 뭘 뜻하는지
몰라서 숫자만 봐도 원인 특정이 어려웠다. 관찰된 비정상 패턴은 Old gen이 220MB에 고착되어
떨어지지 않았고, Full GC 31회 / 총 51.3초가 쌓여 요청 시간의 상당 부분이 GC pause였다. Young
GC도 789회로 할당률이 매우 높았다.

라이브러리 교체(xlsx-streamer → fastexcel-reader)와 chunk 사이즈 축소(1000 → 200)로 해결은
했지만, "왜 이 숫자들이 위험 신호였는지"를 GC 메커니즘으로 설명할 수 없는 상태. 다음에 비슷한
문제가 오면 또 감으로 때려맞춰야 한다. "숫자만 보고 즉시 판단할 수 있는 감각"이 목표.

## 핵심 질문 (학습의 나침반)

학습이 끝났을 때 본인 말로 답할 수 있어야 할 3개:

1. **Q1 (원인)**: 왜 OOM 때 Old gen만 220MB에 고착되었는가? Young gen은 Minor GC로 비워졌는데
   Old는 왜 안 비워졌나? — Promotion 조건과 Full GC 동작으로 설명할 것.
2. **Q2 (선택 판단)**: 이 상황에서 `-Xmx`를 2GB로 늘리는 것과 chunk size를 줄이는 것 중 어느
   쪽이 옳았나? 그리고 왜 GC 알고리즘 변경(G1 → Parallel)은 답이 아니었나?
3. **Q3 (관찰)**: `jstat -gc` 출력에서 `OU 220000` · `FGC 31` · `FGCT 51.3` 이 세 숫자가
   동시에 나타날 때 어떤 상태를 의미하나? 각각 정상/경고/위험 어느 쪽이고 왜?

> 책/글 읽다가 이 답이 나오는 부분이 오면 멈춰서 본인 언어로 메모. 안 나오면 스킵.

## 학습 레이어

| 순서 | 레이어 | 핵심 질문 | 예상 시간 |
|---|---|---|---|
| 1 | Heap 영역 구조 (Young: Eden/S0/S1, Old, Metaspace) | 왜 세대(generation)로 나눴는가?<br>Weak Generational Hypothesis | 1h |
| 2 | 객체 생명주기와 Promotion (Eden → S0↔S1 → Old) | 언제 Old로 승격되나? age threshold,<br>premature promotion | 1h |
| 3 | Minor GC vs Full GC, Stop-the-world | 왜 Full GC가 훨씬 비싼가?<br>STW 범위와 스캔 대상 차이 | 1~2h |
| 4 | Allocation rate & GC 압박 | 할당률이 높으면 왜 Old까지 오염되나?<br>(chunk 1000→200이 먹힌 이유) | 1h |

## 추천 자료 (3개 이하)

- **Naver D2 — "Java Garbage Collection"**: 한국어 블로그 글, 30~40분 분량, 입문~중급. 세대별
  구조와 GC 동작을 한 번에 정리하는 가장 빠른 자료. `"naver d2 java garbage collection"`으로
  검색.
- **Oracle HotSpot VM GC Tuning Guide**: 영어 공식 문서, 레퍼런스용. 처음부터 읽지 말고
  레이어별로 필요한 섹션만 찾아볼 것 (특히 "Generations", "Young Generation Collection", "Full
  Collection"). `"HotSpot Virtual Machine Garbage Collection Tuning Guide"`로 검색.
- **(선택)** jstat 컬럼 레퍼런스: 공식 `jstat` man 페이지 또는 `-gc` 옵션 설명. 레이어 5에서만
  참조.

> 3개 이상 찾아보지 말 것. 산만해진다. Naver D2 하나 + 실제 프로젝트 jstat 로그가 이 주제의
80%.

## 검증 (직접 해봐야 하는 것)

최소 3개는 반드시 수행:

- [ ] 실제 프로젝트에서 `-Xlog:gc*:file=gc.log` 또는 `-verbose:gc`로 GC 로그를 찍고, 생성된
  로그를 한 줄씩 해석해보기 (xlsx-streamer 시절과 fastexcel 전환 후 비교할 수 있으면 최고)
- [ ] **(필수)** `jstat -gc <pid> 1s`를 띄워놓고, 작은 Spring Boot 앱에서 큰 List를 반복
  생성하는 코드를 돌려 `EU`가 차다가 `YGC`가 오르는 걸 눈으로 확인
- [ ] **(필수)** 간단한 Kotlin/Java 코드로 Full GC 강제 유발 — 큰 `ByteArray`를 여러 개 만들어
  Old로 승격되도록 하고 `FGC` 카운터 증가 관찰
- [ ] Heap dump 한 번 떠보기: `jcmd <pid> GC.heap_dump heap.hprof` — 이슈 #6 예고편 겸
- [ ] **(필수)** 핵심 질문 Q1~Q3에 본인 언어로 답 작성 → TIL 블로그 글 초안

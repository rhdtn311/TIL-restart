# ArrayList vs HashMap — 자료구조 선택이 메모리에 미치는 영향

## 배경

앞서 Heap dump로 원인 객체를 특정하는 법을 배웠다. 이번에는 한 단계 더 들어가서, **자료구조 선택이 메모리 사용에 얼마나 영향을 주는지**를 메커니즘으로 설명한다.

xlsx-streamer는 SST(SharedStringsTable)를 `HashMap<Integer, String>`으로 저장했고, fastexcel은 `ArrayList<String>`으로 저장했다. 같은 데이터를 담는데 자료구조만 바꿔도 메모리 차이가 발생한다. 단, 본인 OOM 케이스의 96MB 차이 전체를 자료구조만으로 설명할 수는 없다. 자료구조는 한 요인일 뿐, 다른 요인은 이후 글에서 다룬다.

## 메모리 단위 기초

JVM에서 객체가 메모리를 어떻게 차지하는지 이해하려면 다음 도구가 필요하다.

**자료형별 크기:**

| 타입 | 크기 |
|------|------|
| boolean, byte | 1바이트 |
| short, char | 2바이트 |
| int, float | 4바이트 |
| long, double | 8바이트 |
| 객체 참조 (compressed oops) | 4바이트 |

64비트 JVM에서 Heap이 32GB 이하면 compressed oops가 적용되어 참조가 4바이트로 압축된다. 거의 모든 실무 환경이 여기 해당한다.

**객체 헤더:**

모든 객체는 자기 데이터 외에 **객체 헤더**를 추가로 가진다.

- Mark Word: 8바이트 (GC 정보, 락 상태, hashCode 등)
- Klass Pointer: 4바이트 (이 객체가 어떤 클래스인지)
- **합계: 12바이트**

여기에 JVM은 객체 크기를 **8바이트 단위로 정렬**한다. 그래서 데이터 + 헤더가 13바이트면 총 16바이트로 패딩된다.

## ArrayList의 메모리 구조

ArrayList 내부는 단순하다. `Object[]` 배열 하나에 객체 참조를 순서대로 저장한다.

```
주소:    0x1000   0x1004   0x1008   0x100C   0x1010
       ┌────────┬────────┬────────┬────────┬────────┐
배열:  │ ref[0] │ ref[1] │ ref[2] │ ref[3] │ ref[4] │
       └────────┴────────┴────────┴────────┴────────┘
```

각 칸은 4바이트(참조)이고, 메모리에 연속으로 저장된다.

**인덱스 접근이 O(1)인 이유:** `list.get(3)`을 호출하면 JVM은 `시작 주소 + (3 × 4)`로 즉시 위치를 계산한다. 곱셈 한 번 + 덧셈 한 번. 인덱스가 0이든 99,999이든 비용이 동일하다.

**원소 1개당 메모리 오버헤드: 4바이트** (참조 1개)

## HashMap의 메모리 구조

HashMap도 내부에 배열이 있지만 구조가 다르다. 버킷 배열(`Node[] table`)을 가지고, 각 항목은 **Node 객체로 감싸서** 저장한다.

```java
static class Node<K,V> {
    final int hash;      // 4바이트
    final K key;         // 4바이트 (참조)
    V value;             // 4바이트 (참조)
    Node<K,V> next;      // 4바이트 (참조, 충돌 시 연결리스트)
}
```

**Node 1개의 크기:**
- 객체 헤더: 12바이트
- hash + key + value + next: 16바이트
- 합계: 28바이트 → 8바이트 정렬로 **32바이트**

여기에 버킷 배열의 슬롯 4바이트까지 포함하면 항목당 약 **36바이트**.

**put 동작:**
1. `key.hashCode()`로 hash 값 계산
2. `hash % 배열크기`로 버킷 인덱스 결정
3. 해당 버킷에 Node 객체를 만들어서 저장

## 두 자료구조의 메모리 오버헤드 비교

같은 데이터 N개를 담을 때:

| N | ArrayList 오버헤드 | HashMap 오버헤드 | 차이 |
|---|-------------------|------------------|------|
| 100 | 400B | 3.6KB | 3.2KB |
| 10,000 | 40KB | 360KB | 320KB |
| 100,000 | 400KB | 3.6MB | 3.2MB |
| 1,000,000 | 4MB | 36MB | 32MB |
| 10,000,000 | 40MB | 360MB | 320MB |

**원소당 차이는 32바이트**로 작지만, 규모가 커질수록 영향이 비례해서 커진다. 수만 개 미만에서는 무시해도 되지만, 수백만 개부터는 자료구조 선택이 OOM을 가르는 수준이 된다.

## 자료구조 선택 기준

이 두 자료구조는 **무엇을 빠르게 조회할 것인가**에 따라 적합성이 갈린다.

| 조회 패턴 | ArrayList | HashMap |
|-----------|-----------|---------|
| N번째 원소 (인덱스 → 값) | O(1) ✓ | O(1) (가능하지만 메모리 낭비) |
| 특정 값이 있는지 (값 → 인덱스) | O(N) | O(1) ✓ |

**원칙: 같은 시간복잡도라면 메모리 효율이 좋은 쪽을 쓴다.**

## SST에 ArrayList가 옳은 이유

xlsx 파일은 다음 구조로 데이터를 저장한다:

**시트 (sheet1.xml):** 각 셀은 SST의 인덱스 번호만 참조
```xml
<c r="A1" t="s"><v>0</v></c>   <!-- A1셀의 값은 SST의 0번 -->
<c r="B1" t="s"><v>1</v></c>   <!-- B1셀의 값은 SST의 1번 -->
```

**SST (sharedStrings.xml):** 문자열을 번호 순서대로 저장
```xml
<si>홍길동</si>   <!-- 0번 -->
<si>주소</si>     <!-- 1번 -->
```

읽기 전용 라이브러리가 셀 값을 가져오는 흐름은 항상 **"N번째 문자열을 줘"** — 인덱스 → 값 형태다. 문자열을 키로 검색하는 일이 없다.

이 패턴에서:
- ArrayList: 인덱스 조회 O(1) + 메모리 효율 ✓
- HashMap: 인덱스 조회 O(1)은 동일하지만 메모리만 약 9배 더 씀

같은 성능에 메모리만 더 쓰니 ArrayList가 옳다. fastexcel은 이 점을 인식하고 ArrayList로 설계했고, xlsx-streamer는 Apache POI의 HashMap 구조를 그대로 물려받아 메모리를 낭비한 셈이다.

## 정리

- 자료구조 선택은 **조회 패턴**에 따라 결정해야 한다.
- 인덱스 조회만 필요하면 ArrayList, 키 검색이 필요하면 HashMap.
- 같은 시간복잡도면 메모리 효율 좋은 쪽을 쓴다.
- 자료구조 차이의 영향은 **규모에 비례**해서 커지며, 수백만 단위에서는 OOM을 가를 수 있다.

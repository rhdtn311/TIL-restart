# Heap Dump로 OOM 원인 객체를 특정하는 법

## 배경

jstat으로 "Old gen 220MB가 고착되어 Full GC 31회로도 회수 불가"라는 위험 신호를 읽는 법을 배웠다. 하지만 220MB가 **구체적으로 무엇으로 채워져 있었는지**는 jstat만으로는 알 수 없다. 이 글은 Heap dump를 떠서 원인 객체를 특정하는 방법을 다룬다.

## Heap Dump란

Heap dump는 **그 순간 Heap에 존재하는 모든 객체의 스냅샷**이다. 어떤 클래스의 객체가 몇 개 있고, 각각 얼마나 메모리를 차지하고, 누가 누구를 참조하고 있는지까지 전부 담겨 있다.

| 도구 | 정보 수준 | 용도 |
|------|-----------|------|
| jstat | 영역별 사용량 (숫자) | 위험 신호 감지 |
| Heap dump | 객체 단위 상세 정보 | 원인 객체 특정 |

## Heap Dump 뜨는 방법

### 1. OOM 발생 시 자동 생성 (운영 환경 권장)

```
-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/path/heap.hprof
```

OOM은 재현이 어려울 수 있으니, 터지는 그 순간을 자동으로 캡처하도록 미리 걸어두는 게 기본이다.

### 2. 실행 중인 프로세스에서 수동 생성

```bash
jcmd <pid> GC.heap_dump /path/heap.hprof
```

OOM까지 안 갔지만 메모리가 수상할 때, 원하는 시점에 직접 뜰 수 있다.

### 3. jmap (레거시)

```bash
jmap -dump:format=b,file=/path/heap.hprof <pid>
```

jcmd가 권장되니 알아만 두면 된다.

결과물은 모두 `.hprof` 파일이다.

## 분석 도구

대표적으로 **Eclipse MAT (Memory Analyzer Tool)**을 쓴다. IntelliJ에도 hprof 뷰어가 있지만 분석 기능이 제한적이라 실무에서는 MAT을 쓰는 경우가 많다.

MAT에서 hprof 파일을 열면 가장 먼저 보여주는 화면이 **Leak Suspects Report** — 비정상적으로 메모리를 많이 잡고 있는 객체 후보를 자동으로 추정해준다. 대부분의 OOM 케이스에서 여기서부터 시작하면 된다.

이외에 자주 쓰는 두 화면:

- **Histogram:** 클래스별로 객체 개수와 메모리 사용량 목록 (shallow size 기준)
- **Dominator Tree:** "이 객체를 지우면 얼마나 해제되는지" 기준으로 정렬한 트리 (retained size 기준)

## Shallow size vs Retained size

이 두 개념의 차이를 모르면 dump를 봐도 진짜 범인을 못 찾는다.

- **Shallow size:** 그 객체 자신만의 메모리 크기. HashMap 객체 자체는 수십 바이트밖에 안 된다.
- **Retained size:** 그 객체를 GC하면 **연쇄적으로 같이 해제되는** 전체 메모리 크기.

예를 들어 HashMap이 String 10만 개를 잡고 있다면:
- HashMap의 shallow size: 수십 바이트
- HashMap의 retained size: String 10만 개의 크기까지 합산

**Histogram에서 String이 80MB로 1위에 보여도, String 자체가 범인이 아닐 수 있다.** String은 Java에서 가장 많이 쓰이는 클래스라 항상 상위에 나온다. 진짜 중요한 건 "그 String들을 누가 잡고 있는가"이고, 이걸 보려면 Dominator Tree를 봐야 한다.

## 실습: 의도적 OOM 유발 후 dump 분석

```kotlin
fun main() {
    val list = mutableListOf<ByteArray>()
    var count = 0
    while (true) {
        list.add(ByteArray(1024 * 1024))
        count++
        println("Allocated: ${count}MB")
    }
}
```

VM options:
```
-Xmx64m -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=./heap.hprof
```

실행하면 60여 번 출력 후 OOM이 터지고, 프로젝트 루트에 `heap.hprof`가 생성된다. 분석해보면:

- **byte[]:** Shallow = 32MB, Retained = 32MB
- 나머지: KB 수준

byte[]는 원시 타입 배열이라 다른 객체를 참조하지 않으니 shallow와 retained가 동일하다. 만약 String 같은 객체를 담는 컨테이너였다면 retained가 훨씬 컸을 것이다.

## OOM 케이스에 적용하는 흐름

xlsx 파싱 OOM 상황에서 만약 dump를 떴다면 이런 순서로 추적할 수 있다:

1. **Leak Suspects Report** — MAT의 자동 추정 결과 확인
2. **Dominator Tree** — retained size 상위 객체 확인
3. **참조 체인 추적** — 해당 객체를 누가 잡고 있는지 GC Root까지 연결

이때 Histogram만 봤다면 String이 1위로 나와서 "문자열이 많네"로 끝났을 수 있다. 하지만 Dominator Tree를 보면 그 String들을 잡고 있는 컨테이너 객체가 retained size 상위에 드러나고, 그게 진짜 원인이 된다.
